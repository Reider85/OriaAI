## 1. Введение: цели и методология

### 1.1 Зачем применять ТРИЗ к архитектуре ПО

ТРИЗ (Теория решения изобретательских задач, Г. Альтшуллер) изначально создавалась для инженерных систем с физическими объектами, однако программная архитектура обладает той же фундаментальной структурой: она состоит из взаимодействующих компонентов (веществ), связанных потоками данных и управления (полями), и подчиняется тем же законам эволюции — росту идеальности, динамизации, переходу в надсистему. Применение ТРИЗ к программным системам особенно продуктивно на этапе, когда архитектура уже оформилась в виде набора ADR и Trade-offs, и команда осознаёт накопленные компромиссы как «технические долги» — то есть как неразрешённые противоречия. В случае LLM Client такой момент наступил: документ `ARCHITECT.md` фиксирует восемь ADR и явный список Trade-offs, в каждом из которых видны классические ТРИЗ-противоречия «улучшение одного параметра ухудшает другой». ТРИЗ даёт систематический аппарат для их разрешения, не скатываясь ни в ad-hoc рефакторинг, ни в paralysis-by-analysis.

Ключевое отличие ТРИЗ от стандартных архитектурных практик (DDD, hexagonal, CQRS) состоит в том, что ТРИЗ работает не с шаблонами решений, а с структурой проблемы. ТРИЗ-анализ не предлагает «перейти на микросервисы» или «внедрить event sourcing» — он формулирует противоречие как логическое отношение между двумя параметрами системы и подбирает минимальное изменение, которое снимает противоречие, а не балансирует его. Это особенно ценно для LLM-стека, где каждый новый «лучший паттерн» часто приносит новый класс проблем (например, semantic cache ускоряет, но создаёт риск устаревших ответов; event sourcing даёт аудируемость, но увеличивает latency).

### 1.2 Применённые инструменты ТРИЗ

В данном анализе использованы пять инструментов ТРИЗ:

1. **ИКР (Идеальный конечный результат)** — формулировка предельного состояния системы, при котором она выполняет свою функцию, не существуя как объект. ИКР используется как «направляющая звезда» для оценки конкретных решений: решение тем ближе к идеальному, чем меньше компонентов оно требует для достижения того же эффекта.

2. **9 законов развития технических систем** — эмпирически установленные тренды эволюции: закон полноты частей, закон сквозного прохода энергии, закон согласования ритмики, закон увеличения степени идеальности, закон неравномерности развития подсистем, закон перехода в надсистему, закон перехода с макро- на микроуровень, закон увеличения вепольности, закон повышения динамичности. Законы применяются как диагностический набор: какая подсистема LLM Client отстаёт, какая переразвита.

3. **40 принципов разрешения технических противоречий** — каталог эвристик, проиндексированный матрицей Альтшуллера (39×39 параметров). Для каждой пары «улучшаемый × ухудшаемый параметр» матрица даёт 3–5 наиболее вероятных принципов. Принципы универсальны (дробление, асимметрия, вынесение, динамичность, фазовый переход и т.д.) и допускают программную интерпретацию.

4. **Su-Field (вепольный) анализ** — моделирование минимальной технической системы из двух веществ (S1, S2) и поля (F), их связывающего. Позволяет классифицировать подсистему как неполную, избыточную или вредную веполь и подобрать стандартное развитие.

5. **Стандартные решения (76 приёмов в 5 классах)** — каталог типовых преобразований вепольных моделей: построение/разрушение веполей, развитие веполей, переход к надсистеме/микроуровню, детектирование/измерение, введение веществ/полей. Применяется, когда противоречие локализовано в конкретной триаде компонентов.

### 1.3 Специфика программной интерпретации

Для целей данного анализа приняты следующие соответствия:

| ТРИЗ-понятие | Программная интерпретация в LLM Client |
|---|---|
| Вещество S1 | Данные (сообщение пользователя, чанк документа, tool-call) или компонент-источник |
| Вещество S2 | Данные (ответ LLM, результат tool) или компонент-приёмник |
| Поле F | Поток управления, сигнал, контракт интерфейса, транспорт (HTTP, stdio, SSE) |
| Изделие | Запрос пользователя или бизнес-функция (поиск, RAG, экспорт) |
| Инструмент | Компонент, воздействующий на изделие (LangGraph, Tool Layer, RAG) |
| Энергия | Вычислительный ресурс, токен-бюджет, время CPU/IO |

Принцип «вещество не существует само по себе, а только в паре с полем» в программной трактовке означает: компонент существует лишь постольку, поскольку у него есть контракт (поле), связывающий его с другими компонентами. Это особенно важно для анализа `tool_registry` и `MCPClientManager`: инструменты без явного поля связи с оркестратором — мёртвый код.

Документ структурирован по линии «диагностика → противоречие → решение»:

- **Раздел 8** углубляется в 4 ключевые триады через Su-Field.

## 2. Контекст: краткая модель анализируемой системы

### 2.1 Системный облик

LLM Client — модульный монолит на Python 3.11 с оркестратором LangGraph, абстракцией LLM-провайдеров через LangChain, UI на Streamlit и тремя альтернативными векторными хранилищами (Chroma / Qdrant / pgvector). Система интегрируется с внешними API (OpenAI, Anthropic, Tavily), MCP-серверами (filesystem, github) и persistence-слоем (PostgreSQL, Redis, локальный volume или S3/MinIO). Семь слоёв архитектуры (Presentation, Orchestration, LLM Provider, Tool, RAG, MCP Client, Persistence) образуют однонаправленную зависимость по принципу onion/hexagonal.

С точки зрения ТРИЗ система имеет чёткое изделие — запрос аналитика, требующий одного из трёх действий: текстового ответа LLM, RAG-поиска по корпоративным документам, или автоматизированной операции через tools (веб-поиск, файловый экспорт, MCP-вызов). Все семь слоёв — это инструменты, последовательно воздействующие на изделие через поля (контракты интерфейсов). Внешние системы (OpenAI, Qdrant, MCP-серверы) — это надсистема, в которую LLM Client встроен как компонент.

### 2.2 ТРИЗ-декомпозиция: вещества и поля

| Подсистема | Вещества (S) | Поля (F) |
|---|---|---|
| Presentation | Сообщения пользователя, артефакты | Streamlit callbacks, SSE-поток |
| Orchestration | `AgentState`, сообщения, tool_calls | Контракт `StateGraph`, conditional edges |
| LLM Provider | Prompt, completion | `BaseChatModel` interface, HTTP API провайдера |
| Tool Layer | Tool args, tool result | `@tool`-декоратор, `BaseTool` контракт, `tool_registry` |
| RAG | Чанк документа, embedding-вектор | Embeddings-функция, `VectorStore` interface |
| MCP Client | MCP-запрос, MCP-ответ | stdio pipe, SSE, WebSocket transports |
| Persistence | Сессия, сообщение, файл, checkpoint | SQLAlchemy async, Redis commands, FS API |

### 2.3 Ключевые функции системы (по бизнес-целям G-1..G-5)

| ID | Функция | Главная полезность | Где реализована |
|---|---|---|---|
| G-1 | RAG-поиск по документам | Сокращение времени аналитика | RAG Layer + Tool Layer (`rag_query`) |
| G-2 | Унифицированный доступ к LLM | Один UI для всех провайдеров | LLM Provider Layer + Settings Panel |
| G-3 | Инструментальный слой | Автоматизация рутины | Tool Layer + MCP Client Layer |
| G-4 | Аудит и воспроизводимость | 100% логирование с trace | Persistence Layer + Observability |
| G-5 | MVP за 3 недели | Time-to-MVP ≤ 15 чел-дн | Streamlit + LangGraph как ускорители |

### 2.4 Что считать противоречием

В архитектуре LLM Client противоречие возникает там, где один ADR прямо улучшает одну бизнес-цель и ухудшает другую. Например: ADR-002 (Streamlit для MVP) ускоряет G-5, но ухудшает G-4 (аудитируемость при multi-instance) и блокирует production-масштаб (G-1 при росте нагрузки). ADR-003 (тройное векторное хранилище) улучшает G-1 (гибкость RAG) и ухудшает G-5 (три имплементации нужно тестировать). Эти зависимости зафиксированы в `ARCHITECT.md` § 8 Trade-offs, но не разрешены — только «смягчены». ТРИЗ-задача — перевести их из разряда trade-off в разряд решённых противоречий.

## 3. ИКР — Идеальный конечный результат

### 3.1 Глобальный ИКР

**ИКР-0 (система в целом)**: Система сама выполняет все функции аналитика по поиску, агрегации и экспорту информации, не существуя как отдельный программный продукт. Аналитик работает в привычных ему инструментах (IDE, браузер, мессенджер), а функции LLM Client «встроены» в эти инструменты — ответы появляются в нужном контексте, файлы сохраняются в нужных местах, RAG-поиск срабатывает при открытии документа.

Признак достижения: ни один стейкхолдер не называет «LLM Client» как продукт — он называется «функция в IDE» / «плагин для Confluence» / «бот в Slack». Самостоятельная инсталляция Streamlit-приложения исчезает.

Глобальный ИКР — недостижимый предел, но он задаёт направление: любая конкретная рекомендация оценивается по тому, приближает ли она систему к ИКР-0 или отдаляет. Например, миграция Streamlit→Chainlit сама по себе нейтральна; приближением к ИКР-0 будет встраивание LLM-функций в IDE через MCP-server mode (ADR-004 уже отложил это до Phase 6 — ТРИЗ-анализ ускоряет этот шаг).

### 3.2 Декомпозиция на компонентные ИКР

#### ИКР-1 (Presentation Layer)

UI сам адаптируется к контексту пользователя, не требуя отдельного «открытия приложения». В пределе — отсутствует как отдельный экран; чат-функция встроена в инструмент, где аналитик уже работает.

Признаки достижения:
- Streamlit-приложение сворачивается до плагина в VS Code / Jupyter / Chainlit embedded mode.
- Сессии синхронизируются между точками входа без явного логина.
- Скачивание файлов «происходит само» — артефакт сохраняется в текущую рабочую директорию пользователя.

#### ИКР-2 (Orchestration Layer)

Граф агента сам настраивается под тип запроса, без явного `planner` узла. Состояние само сохраняется и восстанавливается без явного checkpointing-вызова. Итерации сами прекращаются при достижении достаточности ответа.

Признаки достижения:
- `planner` заменяется на capability-based routing: выбор пути определяется структурой входящего сообщения, без отдельного LLM-вызова.
- Checkpointing асинхронен и неблокирующий; состояние восстанавливается «по требованию» при обращении, а не при каждом шаге.
- `max_iterations` заменяется на семантический критерий достаточности (например, метрика полноты ответа).

#### ИКР-3 (LLM Provider Layer)

LLM сам подбирается под тип задачи в момент вызова, без явной настройки пользователем. Fallback-цепочка исчезает как концепция — вместо неё работает cost-aware routing, выбирающий оптимального провайдера на основе SLA, стоимости и текущей нагрузки.

Признаки достижения:
- В Settings Panel нет поля «провайдер» — есть только предпочтения (стоимость vs скорость vs приватность).
- `LLMProviderFactory` заменяется на `LLMRouter` с политиками выбора.
- Retry/fallback инкапсулированы в роутере, не видны компоненту-вызывающему.

#### ИКР-4 (Tool Layer)

Инструменты сами обнаруживаются из окружения, без явной регистрации в `tool_registry`. Кэш tool-вызовов сам поддерживает актуальность, без явной инвалидации. Tool-calling работает для любой модели, независимо от поддержки function calling.

Признаки достижения:
- `tool_registry` автоматически наполняется из MCP-серверов и OpenAPI-спецификаций внешних API.
- Semantic cache tool-вызовов: повторный запрос с тем же смыслом возвращает кэшированный результат, с автоматической инвалидацией по TTL и контенту.
- Для моделей без function calling (Llama base, Mistral без tool-mode) автоматически включается ReAct-эмуляция через system prompt.

#### ИКР-5 (RAG Layer)

RAG сам выбирает стратегию поиска (vector / BM25 / hybrid / map-reduce) под структуру запроса и характеристики корпуса документов. Чанкование адаптивно: документы с естественной структурой (заголовки, секции) не режутся рекурсивно. Embedding-модель сама подменяется при смене языка документа.

Признаки достижения:
- `RecursiveCharacterTextSplitter` — fallback, не default. Для Markdown/HTML/DOCX используется структурное чанкование.
- Retriever включает reranker по умолчанию (Cohere Rerank / bge-reranker / cross-encoder).
- `VectorStoreFactory` заменяется на plugin-registry: новая имплементация подключается через entrypoint, а не через `match kind:`.

#### ИКР-6 (MCP Client Layer)

Транспорт сам подбирается под окружение (stdio в dev, SSE в docker, WS в prod) без явной конфигурации. MCP-серверы сами аутентифицируются и доказывают свою идентичность. Tool discovery кэшируется с автоматическим обновлением.

Признаки достижения:
- `mcp_servers.json` не содержит поле `transport` — клиент сам определяет оптимальный.
- Каждый MCP-сервер имеет подписанный манифест с разрешёнными tool-ами.
- `tools_cache` инвалидируется по сигналу от сервера (server-driven tool list update), а не по TTL.

#### ИКР-7 (Persistence Layer)

Данные сами распределяются по подходящему хранилищу: горячие сессии — в памяти/Redis, тёплые — в PostgreSQL, холодные trace — в S3 с партиционированием по дате. Бэкапы происходят непрерывно (PITR), не ежедневными dump-ами. Schema мигрируется автоматически при деплое без downtime.

Признаки достижения:
- `messages` таблица партиционируется по `created_at` (monthly), старые партиции переносятся в cold storage.
- `agent_checkpoints` переносятся в Redis с TTL + async-flush в PostgreSQL (write-behind log).
- Alembic миграции применяются через expand/contract pattern без блокировок.

### 3.3 Сводная таблица ИКР

| ИКР | Главная идея | Ключевой признак достижения |
|---|---|---|
| ИКР-0 | Система исчезает, функция остаётся | LLM-функции встроены в инструменты аналитика |
| ИКР-1 | UI адаптивен, не отдельное приложение | Streamlit → embedded plugin |
| ИКР-2 | Граф сам настраивается, checkpoint асинхронен | Capability routing, async state |
| ИКР-3 | LLM подбирается автоматически | Cost-aware router без явного выбора |
| ИКР-4 | Tools самообнаруживаются, кэш само-инвалидится | Plugin registry + semantic cache |
| ИКР-5 | RAG сам выбирает стратегию | Adaptive chunking + reranker default |
| ИКР-6 | Транспорт/аутентификация MCP автоматны | Signed manifests + auto-transport |
| ИКР-7 | Данные сами распределяются по хранилищам | Tiered storage + PITR |

ИКР-1..ИКР-7 используются в следующих разделах как критерий оценки конкретных ТРИЗ-решений: решение тем лучше, чем больше признаков ИКР оно реализует без увеличения сложности системы.

## 4. Анализ по законам развития технических систем

Законы развития применяются как диагностический набор: для каждого закона фиксируется текущее состояние соответствующей подсистемы LLM Client, отклонение от идеального тренда и рекомендация по выравниванию.

### 4.1 Закон полноты частей системы

**Формулировка**: техническая система жизнеспособна, если имеет четыре части: двигатель, трансмиссия, рабочий орган и орган управления. В программной трактовке: источник ресурса, транспорт, исполнитель, контроллер.

**Текущее состояние в LLM Client**:
- Двигатель (источник ресурса): внешние LLM API (OpenAI, Anthropic) — есть.
- Трансмиссия (транспорт): LangChain `BaseChatModel` + LangGraph `StateGraph` — есть.
- Рабочий орган (исполнитель): Tool Layer + RAG Layer + MCP Client — есть.
- Орган управления (контроллер): `planner` node в графе — есть, но слаб.

**Отклонение**: орган управления (`planner`) реализован как один LLM-вызов, принимающий решение «нужны ли tools» бинарно. Это не управление в полном смысле — управление должно учитывать состояние системы (загрузку, кэш, историю итераций) и выбирать оптимальный путь, а не только «tools vs no tools».

**Рекомендация**: развить орган управления до capability-based router (см. ИКР-2 и драфт ADR-016). Внедрить явную модель «достаточности ответа» — семантический критерий, по которому граф решает остановиться, а не счётчик `iteration < max_iterations`.

### 4.2 Закон сквозного прохода энергии

**Формулировка**: сквозной проход энергии через все части системы — необходимое условие её жизнеспособности. В программной трактовке: поток данных от входа до выхода должен проходить через все необходимые компоненты без «узких мест» и без «тупиков».

**Текущее состояние**: основной поток (User → Streamlit → LangGraph → LLM → Tool → LLM → Final answer → User) проходит без тупиков, но с двумя узкими местами:
1. `PostgresSaver` блокирует граф при каждом checkpoint — sync write в БД.
2. `file_export` для pdf/docx/xlsx синхронно блокирует ответ, если Worker отсутствует (MVP).

**Отклонение**: при росте нагрузки (>50 RPS) узкое место 1 даст timeout-ы; при тяжёлых файлах (>10MB PDF) узкое место 2 — UX-провал.

**Рекомендация**: ввести асинхронный write-behind log для checkpointing (ADR-010); ввести обязательный Worker для production с pattern «return job_id immediately, polling/SSE для статуса» (расширение ADR-008).

### 4.3 Закон согласования ритмики частей системы

**Формулировка**: ритм работы всех частей системы должен быть согласован. В программной трактовке: пропускные способности подсистем должны быть согласованы; самая медленная подсистема диктует темп.

**Текущее состояние**:
- LLM API: 5–60 сек на ответ.
- Tavily search: 1–3 сек.
- Qdrant retrieval: 50–200 мс.
- PostgreSQL checkpoint: 10–50 мс.
- Streamlit render: 100–500 мс.

**Отклонение**: Streamlit re-runs (целыйrerender всего UI при каждом событии) конфликтует с низколатентным streaming LLM. UI тратит время на пересборку, когда LLM уже отдал 100 токенов. Также: MCP stdio-транспорт имеет латентность запуска (`npx -y` для `@modelcontextprotocol/server-filesystem` = 2–5 сек cold start), что несогласовано с ожиданиями пользователя.

**Рекомендация**: разделить UI на static-shell + dynamic-content (Streamlit fragments в 1.40+); для MCP ввести persistent-connection pool (один процесс MCP-сервера на инстанс LLM Client, а не spawn per call).

### 4.4 Закон увеличения степени идеальности

**Формулировка**: развитие системы идёт в направлении увеличения доли полезной работы и уменьшения затрат (вес, габариты, энергия). В программной трактовке: рост полезной функциональности при снижении сложности (LOC, зависимостей, точек отказа).

**Текущее состояние**: функциональность MVP = 5 бизнес-целей (G-1..G-5) при ~30 компонентах и 8 ADR. При переходе к Production планируется рост компонентов (Chainlit/FastAPI+Next.js, Worker, LiteLLM, LangSmith, Loki/ELK, Prometheus) — функциональность остаётся прежней, сложность растёт. Степень идеальности падает.

**Отклонение**: явное снижение идеальности при переходе MVP→Production. Каждый «production-ready» компонент добавляет точку отказа, конфигурацию, операционную сложность.

**Рекомендация**: каждое новое ADR должно сопровождаться удалением или упрощением существующего компонента. Целевая метрика: «delta функциональности / delta сложности ≥ 1». Конкретно: внедрение FastAPI+Next.js должно сопровождаться удалением Streamlit полностью (а не сосуществованием), внедрение LangSmith — с удалением части кастомного tracing-а.

### 4.5 Закон неравномерности развития подсистем

**Формулировка**: разные подсистемы развиваются неравномерно; отставание одной становится тормозом для всей системы.

**Текущее состояние**: в LLM Client явно отстаёт **Presentation Layer** (Streamlit single-instance, нет real-time collab, нет mobile) и **MCP Client Layer** (только client mode, нет signed manifests, нет tool discovery caching). Сильно переразвиты **LLM Provider Layer** (три провайдера уже сейчас, хотя нужен один-два) и **RAG Layer** (три векторных хранилища, хотя production-нагрузки ещё нет).

**Отклонение**: неравномерность создаёт «фальшивую зрелость» — команда тратит ресурсы на поддержку переразвитых подсистем (три адаптера VectorStore) при отсутствии критичной функциональности в отстающих (RBAC, audit trail).

**Рекомендация**: заморозить развитие переразвитых подсистем (RAG Layer получает только bugfix, новые фичи — только после Production load evidence); сосредоточить ресурсы на отстающих (RBAC, MCP server trust, observability).

### 4.6 Закон перехода в надсистему

**Формулировка**: исчерпав развитие в рамках текущей системы, дальнейшее развитие идёт в надсистему — объединение с другими системами.

**Текущее состояние**: LLM Client — изолированное приложение. Взаимодействие с другими системами (IDE, Slack, Confluence) не предусмотрено в MVP. ADR-004 явно отложил MCP Server mode до Phase 6.

**Отклонение**: LLM-стек быстро движется к экосистемному подходу (Claude Code, Cursor, Continue.dev — все встраивают LLM в IDE). Изоляция LLM Client ставит его в один ряд с десятками подобных standalone-чатов, теряя конкурентное преимущество.

**Рекомендация**: ускорить ADR-004 (MCP Server mode) — внедрить в Phase 3 вместо Phase 6. Это позволит LLM Client быть инструментом для других агентов и IDE, не теряя собственной UI-функциональности. Дополнительно — embed mode через iframe API для встраивания в Confluence/Notion.

### 4.7 Закон перехода с макро- на микроуровень

**Формулировка**: развитие идёт от макроуровня (крупные дискретные компоненты) к микроуровню (мелкие, гибкие, комбинируемые).

**Текущее состояние**: инструменты в `tool_registry` — крупные дискретные функции (`web_search`, `rag_query`, `file_export`, `mcp_call`). Каждый tool — монолитная операция.

**Отклонение**: нет композиции tools на микроуровне. Например, `web_search` всегда возвращает список результатов, даже когда нужно одно число (факт). LLM вынуждена вызывать `web_search`, потом интерпретировать 5 результатов, потом возможно вызвать ещё раз — макроуровень заставляет платить за лишнее.

**Рекомендация**: ввести «микроинструменты» — compose-able primitives: `web_search_fact(query)` (один факт), `web_search_list(query, n)` (список), `web_search_summary(query)` (короткая выжимка). LangGraph связывает их в pipeline без участия LLM на каждом шаге.

### 4.8 Закон увеличения степени вепольности

**Формулировка**: развитие систем идёт в направлении от неполных веполей к полным, от полных — к двойным, от механических полей — к электромагнитным/химическим.

**Текущее состояние**: основные триады (LLM↔Tool↔External API, User↔LangGraph↔Checkpoint) — полные веполи, но с механическими полями (sync HTTP, sync SQL write). Развития к двойным веполям (введение второго поля для усиления/резервирования) нет.

**Отклонение**: отсутствие второго поля в критичных триадах снижает надёжность. Например, в триаде User↔LangGraph↔Checkpoint только одно поле (SQL write) — при отказе PostgreSQL весь граф останавливается.

**Рекомендация**: ввести вторые поля — Redis как write-ahead buffer для checkpointing; semantic cache для LLM-вызовов как второе поле в triаде LLM↔Tool↔Result. См. раздел 8 (Su-Field) и стандартные решения класса 2.

### 4.9 Закон повышения динамичности

**Формулировка**: развитие идёт от жёстких структур к гибким, адаптивным, с переменными параметрами.

**Текущее состояние**: LangGraph `StateGraph` — декларативный, но статический (граф компилируется при старте). Конфигурация `tool_registry` — статическая (compile-time). Выбор провайдера — статический (per-session).

**Отклонение**: система не адаптируется в runtime. Например, при росте нагрузки на OpenAI нет автоматического переключения на Anthropic; при отказе Tavily нет переключения на DuckDuckGo (только manual fallback в коде).

**Рекомендация**: ввести динамические политики — circuit breaker для провайдеров (auto-fallback при 5 ошибках), dynamic tool registry (время жизни MCP-discovered tools ограничено TTL), adaptive retrieval (если первый retriever вернул мало документов, автоматически запросить с другой стратегией).

### 4.10 Сводка по законам развития

| Закон | Текущее состояние | Отклонение | Приоритет |
|---|---|---|---|
| Полнота частей | Орган управления слаб | Planner → capability router | High |
| Сквозной проход | Два узких места | Async checkpoint + Worker | High |
| Согласование ритмики | Streamlit re-runs vs streaming | Streamlit fragments | Medium |
| Идеальность | Падает при переходе в prod | «delta f / delta complexity ≥ 1» | High |
| Неравномерность | RAG переразвит, UI отстаёт | Заморозить RAG, ускорить UI/Sec | High |
| Переход в надсистему | MCP Server отложен | Ускорить ADR-004 до Phase 3 | Medium |
| Переход на микроуровень | Tools макроуровневые | Микроинструменты + pipeline | Low |
| Вепольность | Поля механические, одиночные | Вторые поля (cache, WAL) | High |
| Динамичность | Статический граф и registry | Circuit breakers, dynamic TTL | Medium |

Законы с приоритетом High формируют ядро рекомендаций разделов 5–9. Законы с Medium-приоритетом отражены в ADR, но не блокируют Phase 1–2. Low-приоритетные (микроуровень) заданы как направление для Phase 5+.

## 5. Технические противоречия и 40 принципов — Часть 1 (Масштабируемость и оркестрация)

В разделах 5–7 разбираются 15 технических противоречий. Для каждого применяется матрица Альтшуллера: по оси X — улучшаемый параметр (одна из 39 характеристик ТРИЗ), по оси Y — ухудшаемый. Матрица даёт 3–5 наиболее вероятных принципов из 40. Далее принцип интерпретируется применительно к архитектуре LLM Client.

### 5.1 Противоречие 1: Streamlit vs горизонтальное масштабирование

**Контекст**: ADR-002 фиксирует Streamlit как UI для MVP и признаёт, что horizontal scaling у Streamlit плохой. ADR-002 планирует миграцию на Chainlit/Next.js в Phase 5, но не даёт моста между Phase 1 и Phase 5.

**Улучшаемый параметр** (ТРИЗ #39 «производительность», узкая трактовка — time-to-MVP): Streamlit даёт UI за 3 дня.
**Ухудшаемый параметр** (ТРИЗ #14 «стабильность состава» / #35 «адаптивность»): Streamlit single-instance = узкое место при >5 concurrent users.

**Принципы из матрицы** (39 × 14 → наиболее вероятные принципы):
- **Принцип 1 (Дробление)**: разделить UI на shell (Streamlit) и dynamic content (отдельный процесс/контейнер).
- **Принцип 15 (Динамичность)**: сделать UI swappable через абстракцию `UIClient` с двумя реализациями.
- **Принцип 17 (Переход в другое измерение)**: вынести session_state из Streamlit во внешний session store (Redis), что отвязывает сессию от конкретного инстанса.
- **Принцип 35 (Изменение параметров)**: переключатель `UI_BACKEND=streamlit|chainlit|fastapi` в конфиге, без перекомпиляции.

**Архитектурное решение**: ввести abstraction `UIClient` с интерфейсом `render_message`, `render_artifact`, `stream_token`, `handle_user_input`. Реализации: `StreamlitClient` (MVP), `ChainlitClient` (Alpha), `FastAPIClient` (Production). Session state выносится в `SessionStore` (Redis), что снимает sticky-session constraint. Это не «миграция», а «параллельное существование» — Streamlit не удаляется до полного перехода, но новая функциональность (multi-user, real-time collab) сразу пишется под `UIClient`, а не под Streamlit-specific API.

**Драфт ADR-018**: External Session Store for Streamlit (см. раздел 11).

**Связь с ИКР**: приближает ИКР-1 (UI адаптивен), не блокирует ИКР-0 (функция встраивается в инструменты).

### 5.2 Противоречие 2: PostgreSQL checkpoint vs latency

**Контекст**: ADR-001 использует `PostgresSaver` для LangGraph checkpointer — персистентное состояние графа, resume-after-restart. ADR-005 фиксирует PostgreSQL как primary datastore. Каждый node графа делает sync write в `agent_checkpoints` таблицу.

**Улучшаемый параметр** (ТРИЗ #31 «надёжность/восстанавливаемость»): checkpoint даёт resume после рестарта.
**Ухудшаемый параметр** (ТРИЗ #25 «время» / #9 «скорость»): sync write добавляет 10–50 мс на каждый node transition.

**Принципы из матрицы** (31 × 25):
- **Принцип 9 (Предварительное противодействие)**: писать в Redis (in-memory) синхронно, в PostgreSQL — асинхронно batch-ами.
- **Принцип 19 (Периодическое действие)**: snapshot не каждый node, а каждый N-ный node + на critical points (после tool_call, перед human_review).
- **Принцип 28 (Замена механики)**: заменить sync SQL write на append-only WAL (write-ahead log) с последующим periodic flush.
- **Принцип 35 (Изменение параметров)**: изменить физическое состояние — hot state в Redis, cold state в PostgreSQL.

**Архитектурное решение**: ввести двухуровневый checkpointer: `RedisCheckpointer` (synchronous, low-latency, TTL=24h) + `PostgresCheckpointer` (asynchronous, batched, durable). LangGraph `StateGraph` использует интерфейс `BaseCheckpointSaver`, реализация — composite. На каждом node transition пишется только в Redis (latency <1 мс). Background-task каждые 5 секунд (или N checkpoints) сбрасывает порцию в PostgreSQL. При restart система сначала восстанавливает из PostgreSQL, затем догоняет из Redis (если он жив).

**Драфт ADR-010**: Async Checkpoint Write-Behind Log (см. раздел 11).

**Связь с ИКР**: приближает ИКР-2 (checkpoint асинхронен, «сам сохраняется»).

### 5.3 Противоречие 3: Тройное векторное хранилище vs сложность тестирования

**Контекст**: ADR-003 вводит `VectorStoreFactory` с тремя адаптерами (Chroma, Qdrant, pgvector). В § 8 Trade-offs явно указано: «три имплементации нужно тестировать». Команда из 2 разработчиков на MVP не может поддерживать contract tests для трёх адаптеров с приличным покрытием.

**Улучшаемый параметр** (ТРИЗ #35 «адаптивность» / #32 «изготовляемость»): три адаптера = гибкость, no vendor lock-in.
**Ухудшаемый параметр** (ТРИЗ #36 «сложность устройства» / #37 «сложность контроля»): три имплементации = рост surface area для тестирования.

**Принципы из матрицы** (35 × 36):
- **Принцип 1 (Дробление)**: выделить «thin adapter» (только CRUD) и «thick adapter» (filtering, hybrid search, BM25) — три thin-адаптера + один thick общий.
- **Принцип 3 (Местное качество)**: каждый адаптер специализируется на своей нише (Chroma = embedded, Qdrant = high-load, pgvector = JOIN с бизнес-данными), не пытаясь быть универсальным.
- **Принцип 25 (Самообслуживание)**: adapters self-register через entrypoint (`pyproject.toml` `[project.entry-points."llm_client.vector_stores"]`), `VectorStoreFactory` исчезает — вместо него `VectorStoreRegistry`.
- **Принцип 5 (Объединение)**: объединить функции векторного поиска и метаданных в pgvector для всех окружений, упразднив Chroma (только test-mock) и Qdrant (только при доказанной необходимости).

**Архитектурное решение**: комбинированный подход — принцип 25 (self-registration) + принцип 3 (специализация). Адаптеры регистрируются через entrypoints; `VectorStoreFactory` заменяется на `VectorStoreRegistry.get(name)`. Каждый адаптер декларирует свой профиль (через метаданные: `embedded`, `distributed`, `colocated_with_pg`), и `RetrieverConfig` выбирает адаптер по профилю, а не по имени. Chroma остаётся только как test-double, не как production-опция.

**Драфт ADR-009**: Plugin-based VectorStore Registry (см. раздел 11).

**Связь с ИКР**: ИКР-5 (RAG сам выбирает стратегию) — `RetrieverConfig` выбирает адаптер по профилю.

### 5.4 Противоречие 4: SSE one-way vs real-time interactivity

**Контекст**: ADR-007 зафиксировал SSE для streaming LLM-ответов. В § Consequences указано: «One-way only: для интерактивных прерываний (cancel button) нужно доп. HTTP endpoint». Это означает, что для cancel-кнопки нужен отдельный HTTP POST, что нарушает UX (нажатие cancel не мгновенно — ждём HTTP round-trip, потом агент должен проверить флаг).

**Улучшаемый параметр** (ТРИЗ #32 «изготовляемость» / #12 «равномерность конструкции»): SSE проще, работает через любой reverse proxy, auto-reconnect.
**Ухудшаемый параметр** (ТРИЗ #34 «ремонтопригодность» / #26 «удобство»): one-way — cancel/delay/replay требует отдельных механизмов.

**Принципы из матрицы** (32 × 34):
- **Принцип 15 (Динамичность)**: сделать транспорт адаптивным — SSE для streaming out, HTTP POST для control in. Это не «или/или», а «и/и» с разными ролями.
- **Принцип 26 (Копирование)**: вместо сложного WebSocket — простой HTTP-канал управления + SSE-канал данных. Один дублирует функциональность другого для критичных операций.
- **Принцип 13 (Наоборот)**: вместо того, чтобы пользователь отменял — агент сам детектирует «пользователь ушёл» (SSE-соединение закрылось) и отменяет upstream LLM-вызов.
- **Принцип 17 (Переход в другое измерение)**: вынести cancel-логику в отдельный control-plane (Redis pub/sub), не смешивать с data-plane.

**Архитектурное решение**: комбинированный принцип 15 + 13. Ввести два канала: data-plane (SSE, как сейчас) и control-plane (HTTP POST `/sessions/{id}/cancel` + Redis pub/sub для уведомления агента). Дополнительно — детектор «обрыв SSE-соединения» в UI-клиенте, который автоматически шлёт cancel, если пользователь закрыл вкладку. На стороне агента — cancellation token, проверяемый в каждой итерации графа (между node-ами).

**Драфт ADR-013**: SSE + HTTP Cancel Endpoint (см. раздел 11).

**Связь с ИКР**: ИКР-2 (граф сам настраивается) — cancel «происходит сам» при уходе пользователя.

### 5.5 Противоречие 5: LangGraph cycles vs детерминизм

**Контекст**: ADR-001 выбирает LangGraph ради циклов, conditional edges, human-in-the-loop. Однако `max_iterations=10` — единственная защита от зацикливания. Циклы в графе могут привести к бесконечному tool calling, если LLM «зациклится» на одном инструменте.

**Улучшаемый параметр** (ТРИЗ #35 «адаптивность» / #4 «неоднородность»): cycles + conditional edges = гибкая логика.
**Ухудшаемый параметр** (ТРИЗ #31 «надёжность» / #27 «долговечность»): потенциальные infinite loops.

**Принципы из матрицы** (35 × 31):
- **Принцип 19 (Периодическое действие)**: вместо счётчика итераций — семантический критерий: проверка «ответ достаточно полный?» каждые N итераций через отдельную LLM-оценку (judge).
- **Принцип 23 (Обратная связь)**: ввести feedback-loop — после каждой итерации оценивать delta между текущим состоянием и предыдущим; если delta < threshold — выйти.
- **Принцип 22 (Превращение вреда в пользу)**: использовать сам факт зацикливания как сигнал — LLM «застряла», переключить стратегию (другой tool, другой retriever, другой провайдер).
- **Принцип 11 (Заранее подложенная подушка)**: pre-emptive guard — перед каждой итерацией проверять «мы уже видели этот tool_call в этой сессии?», если да — изменить параметры (разный prompt, разные args).

**Архитектурное решение**: комбинированный принцип 23 + 22. Ввести `iteration_monitor` node после каждого tool execution: считает delta между новым state и предыдущим (через embedding diff в `messages`). Если delta < threshold (например, cosine similarity > 0.95 между последними двумя сообщениями) — это сигнал «зацикливания», граф переключается в режим «escalation»: меняет prompt на «ты повторяешься, попробуй другой подход», либо переключает провайдера, либо возвращает текущий ответ как final.

**Драфт ADR (без номера — расширение ADR-001)**: Cycle Detection via State Delta (см. раздел 11, расширение ADR-001).

**Связь с ИКР**: ИКР-2 (граф сам настраивается, итерации сами прекращаются) — прямой hit.

## 6. Технические противоречия — Часть 2 (Надёжность и стоимость)

### 6.1 Противоречие 6: Длинный контекст RAG vs стоимость LLM

**Контекст**: § 12 (Открытые вопросы) Q-5 фиксирует риск: при RAG с >50k токенов контекста стоимость LLM-вызова становится доминирующей. Текущая митигация — context compression через `LLMChainExtractor`, map-reduce для длинных документов. Это частичное решение, не устраняющее противоречие.

**Улучшаемый параметр** (ТРИЗ #28 «точность измерения» / #14 «стабильность состава»): больше контекста = точнее ответ.
**Ухудшаемый параметр** (ТРИЗ #22 «потери энергии» / #39 «производительность»): больше контекста = выше стоимость и latency.

**Принципы из матрицы** (28 × 22):
- **Принцип 16 (Частичное/избыточное действие)**: сначала «избыточно» — достаём 20 чанков, потом «частично» — reranker оставляет 5. Текущий MMR делает это, но без ML-reranker.
- **Принцип 21 (Сканирование вперёд)**: pre-compute likely queries для документа — semantic cache, который при поступлении нового документа anticipates возможные запросы и хранит готовые ответы на top-N вероятных вопросов.
- **Принцип 9 (Предварительное противодействие)**: кэшировать embeddings жёстко (документ не меняется — embedding не перевычисляется). Текущая имплементация делает это, но не использует кэш на уровне LLM-ответов.
- **Принцип 17 (Переход в другое измерение)**: вынести «понимание документа» на индекс-тайм — извлечь факты (entity extraction, summarization) при индексации, не при запросе. RAG-запрос идёт по фактам, не по сырым чанкам.

**Архитектурное решение**: комбинированный принцип 16 + 17 + 21. Ввести three-tier retrieval:
1. **Tier 1 — Facts cache**: при индексации документа извлекаются факты (через LLM), хранятся отдельно, индексируются как metadata.
2. **Tier 2 — Vector retrieval**: текущий pipeline, но с cross-encoder reranker (bge-reranker-base или Cohere Rerank).
3. **Tier 3 — Semantic answer cache**: cache полных ответов на типовые запросы (с автоматической инвалидацией при изменении документа).

При запросе LLM Client сначала проверяет Tier 3 (точный ответ?), затем Tier 1 (факты для ответа?), затем Tier 2 (полные чанки). Это снижает среднее число токенов в контексте на 60–80%.

**Драфт ADR-011**: Hybrid Semantic Cache for LLM (см. раздел 11).
**Драфт ADR-017**: Reranker Model in RAG (см. раздел 11).
**Драфт ADR-020**: Hybrid (BM25 + vector) RAG по умолчанию (см. раздел 11).

**Связь с ИКР**: ИКР-5 (RAG сам выбирает стратегию) — three-tier retrieval это и есть адаптивность.

### 6.2 Противоречие 7: Fallback chain vs предсказуемость стоимости

**Контекст**: § 5.2.3 описывает `fallback_chain` — автоматическое переключение на Anthropic при 5 ошибках OpenAI подряд. В § 9.4 Security указан бюджет на пилот $500/мес на команду из 5 пользователей. Стоимость GPT-4o ($5/1M input) и Claude 3.5 Sonnet ($3/1M) различается почти в 1.7×. Слепой fallback может превысить бюджет.

**Улучшаемый параметр** (ТРИЗ #31 «надёжность»): fallback повышает availability.
**Ухудшаемый параметр** (ТРИЗ #22 «потери энергии» / #30 «вредные факторы извне»): непредсказуемый cost drift при fallback.

**Принципы из матрицы** (31 × 22):
- **Принцип 35 (Изменение параметров)**: ввести cost-aware routing — fallback выбирает не «следующий по списку», а «оптимальный по соотношению цена/SLA в текущий момент».
- **Принцип 16 (Частичное/избыточное действие)**: частичный fallback — при перегрузке OpenAI переключаем не весь трафик, а 30%; остальное держим с retry.
- **Принцип 13 (Наоборот)**: вместо «fallback при ошибке» — «load balancing по умолчанию»: трафик распределяется между провайдерами 70/30 в обычном режиме, fallback при ошибке только меняет пропорцию.
- **Принцип 23 (Обратная связь)**: real-time cost metering с auto-decision: при достижении 80% месячного бюджета fallback переключается на самую дешёвую опцию (GPT-4o-mini / Claude Haiku / Ollama).

**Архитектурное решение**: комбинированный принцип 35 + 23. Ввести `LLMRouter` (см. также ИКР-3), который:
1. Хранит политики выбора (cost priority / latency priority / quality priority).
2. Получает real-time метрики от `token_usage_tracker` и `cost_tracker`.
3. Принимает решение о routing на каждый запрос на основе: текущей нагрузки на провайдера (circuit breaker), текущего расхода бюджета (cost guard), требований к приватности (zero-retention policy).
4. Fallback — крайний случай; обычно routing распределяет заранее.

**Драфт ADR-015**: Cost-Aware Routing (см. раздел 11).

**Связь с ИКР**: ИКР-3 (LLM сам подбирается под задачу) — точное попадание.

### 6.3 Противоречие 8: MCP stdio в docker-compose vs изоляция

**Контекст**: § 12 Q-3 фиксирует: MCP-серверы с stdio-транспортом в docker-compose создают сложность. Каждый MCP-сервер spawn-ится как subprocess внутри контейнера LLM Client, что нарушает изоляцию и затрудняет оркестрацию. Cold start `npx -y @modelcontextprotocol/server-filesystem` = 2–5 секунд на первый вызов.

**Улучшаемый параметр** (ТРИЗ #32 «изготовляемость» / #12 «равномерность конструкции»): stdio проще, не требует HTTP-сервера, нативно работает локально.
**Ухудшаемый параметр** (ТРИЗ #31 «надёжность» / #36 «сложность устройства»): stdio в docker = subprocess management, нет нормальной изоляции, cold start.

**Принципы из матрицы** (32 × 31):
- **Принцип 17 (Переход в другое измерение)**: вынести MCP-серверы в отдельные sidecar-контейнеры с SSE-транспортом — каждый MCP-сервер становится долгоживущим сервисом, не subprocess.
- **Принцип 2 (Вынесение)**: вынести транспортный слой из MCPClientManager в отдельный `MCPTransport` с двумя реализациями (stdio, SSE), выбран автоматически по окружению.
- **Принцип 28 (Замена механики)**: заменить stdio-pipe на HTTP для всех MCP-серверов в production; stdio оставить только для dev.
- **Принцип 1 (Дробление)**: разделить MCPClientManager на `ConnectionManager` (transport) и `ToolRegistry` (semantic).

**Архитектурное решение**: комбинированный принцип 2 + 17. Ввести `MCPTransport` абстракцию с двумя реализациями: `StdioTransport` (dev, embedded) и `SSETransport` (docker, sidecar). Выбор транспорта — по конфигурации сервера, не по приложению. В docker-compose каждый MCP-сервер — отдельный сервис с healthcheck, restart policy, resource limits. `MCPClientManager` автоматически определяет живой транспорт (через probe) и переключается при отказе.

**Драфт ADR-012**: MCP Transport Auto-Negotiation (см. раздел 11).

**Связь с ИКР**: ИКР-6 (транспорт сам подбирается под окружение).

### 6.4 Противоречие 9: Tool calling API vs переносимость моделей

**Контекст**: ADR-006 зафиксировал нативный tool calling через `bind_tools()` LangChain. В § Consequences: «Локальные модели без function calling (Llama 3.1 base) — не поддерживаются в MVP». Это блокирует ADR-004 roadmap на Phase 4 (Ollama).

**Улучшаемый параметр** (ТРИЗ #28 «точность» / #32 «изготовляемость»): нативный tool calling — надёжный парсинг, меньше токенов на системный промпт.
**Ухудшаемый параметр** (ТРИЗ #14 «стабильность состава» / #35 «адаптивность»): vendor lock-in на модели с function calling.

**Принципы из матрицы** (28 × 14):
- **Принцип 13 (Наоборот)**: вместо «один режим для всех» — инвертировать: ReAct как базовый режим, function calling как оптимизация для моделей, которые его поддерживают.
- **Принцип 35 (Изменение параметров)**: ввести `ToolCallingMode` enum (`native`, `react`, `hybrid`); adapter выбирает режим по capability-матрице модели.
- **Принцип 1 (Дробление)**: разделить «описание tool» (единый для всех моделей) и «вызов tool» (специфичный для режима).
- **Принцип 25 (Самообслуживание)**: модели сами декларируют свои capabilities через capability matrix (registry), adapter выбирает стратегию автоматически.

**Архитектурное решение**: комбинированный принцип 35 + 25. Ввести `ModelCapabilityMatrix` — для каждой модели известны: `supports_native_tools`, `supports_streaming`, `supports_vision`, `context_window`, `cost_per_1m_tokens`. `LLMRouter` (из противоречия 7) использует эту матрицу для выбора не только провайдера, но и `ToolCallingMode`. Для моделей без native function calling автоматически включается ReAct-эмуляция через system prompt (LangChain `ReActAgentExecutor` или кастомный graph node).

**Драфт ADR-016**: Tool Capability Adapter (см. раздел 11).

**Связь с ИКР**: ИКР-3 (LLM подбирается автоматически) + ИКР-4 (tool calling работает для любой модели).

### 6.5 Противоречие 10: Синхронный file rendering vs response latency

**Контекст**: § 6.4 показывает поток file_export — в MVP синхронный, в production через Worker (Celery/RQ). В § 9.1 Performance: target «File export (1 MB PDF) < 5 сек». На деле 1MB PDF через reportlab = 3–8 сек в зависимости от сложности, что нарушает target.

**Улучшаемый параметр** (ТРИЗ #32 «изготовляемость» / #4 «неоднородность»): sync в MVP = проще, нет инфраструктуры.
**Ухудшаемый параметр** (ТРИЗ #25 «время» / #24 «функциональные потери»): sync = блокировка ответа, превышение latency target.

**Принципы из матрицы** (32 × 25):
- **Принцип 9 (Предварительное противодействие)**: для типовых форматов (md, txt) — sync; для тяжёлых (pdf, docx, xlsx, odt) — async с моментальным возвратом job_id.
- **Принцип 19 (Периодическое действие)**: batch rendering — несколько небольших файлов в одном Worker job.
- **Принцип 28 (Замена механики)**: заменить тяжёлые рендереры (reportlab) на лёгкие (PDF через Playwright + HTML template) для случаев, где допустимо.
- **Принцип 21 (Сканирование вперёд)**: pre-render часто запрашиваемых шаблонов (корпоративный логотип в PDF, типовой шаблон отчёта) — кэш готовых «скелетов».

**Архитектурное решение**: комбинированный принцип 9 + 28. Разделить форматы на две группы:
1. **Fast formats** (md, txt, csv, json): sync, мгновенный возврат.
2. **Slow formats** (pdf, docx, xlsx, odt): async с моментальным возвратом `job_id`, polling/SSE для статуса.

Для PDF — заменить reportlab на Playwright + HTML template (для типовых отчётов) — это даёт лучшее качество и меньшую latency (1–2 сек вместо 5–8). Reportlab оставить для случаев с программно-генерируемыми таблицами/графиками.

**Драфт ADR (расширение ADR-008)**: Async File Rendering with Format-Specific Backends (см. раздел 11).

**Связь с ИКР**: ИКР-1 (файлы «сами сохраняются» в нужном месте) — async rendering + auto-save в рабочую директорию.

## 7. Технические противоречия — Часть 3 (Безопасность и dev-prod паритет)

### 7.1 Противоречие 11: PII masking vs observability

**Контекст**: § 9.4 Security фиксирует: в MVP — regex-based PII masking, в Production — Microsoft Presidio + custom rules. § 9.6 Observability: «100% запросов логируются с full trace, retention 90 дней». Если маскировать PII в логах — теряется воспроизводимость trace (нельзя повторить запрос с теми же данными). Если не маскировать — нарушение GDPR/SOC2.

**Улучшаемый параметр** (ТРИЗ #31 «надёжность» / #9 «скорость»): full trace = воспроизводимость, возможность debug.
**Ухудшаемый параметр** (ТРИЗ #31 «надёжность» в другом смысле / #30 «вредные факторы»): PII в логах = compliance risk.

**Принципы из матрицы** (особый случай — это физическое противоречие: один и тот же параметр «trace detail» должен быть и высоким, и низким):
- **Принцип 17 (Переход в другое измерение)**: разделить логи на два потока — operational (маскированный, для debugging и monitoring) и forensic (зашифрованный, для аудита и расследований). Доступ к forensic — отдельный RBAC.
- **Принцип 3 (Местное качество)**: разные уровни маскирования для разных окружений (dev = no mask, staging = partial mask, prod = full mask + forensic).
- **Принцип 22 (Превращение вреда в пользу)**: использовать PII detection как feature — автоматически классифицировать запросы по чувствительности (low/medium/high), high-PII запросы идут в secure-режим (без логирования контента, только метаданные).
- **Принцип 26 (Копирование)**: копировать trace дважды — masked operational + encrypted forensic; ключи шифрования в KMS, не в приложении.

**Архитектурное решение**: комбинированный принцип 17 + 26. Ввести `DualStreamLogger`:
1. **Operational stream**: маскированный (Presidio + regex), отправляется в stdout/Loki/ELK, retention 30 дней. Используется командой для debugging.
2. **Forensic stream**: зашифрованный (AES-256-GCM с ключом из KMS/Vault), отправляется в отдельное хранилище (S3 с server-side encryption), retention 90+ дней. Доступ через отдельный RBAC-процесс (только security officer + аудит-комитет).

Дополнительно (принцип 22): PII detection score сохраняется в `messages` таблице как metadata, что позволяет строить аналитику «какую долю запросов составляет sensitive data» и адаптировать политики.

**Драфт ADR-014**: Dual-Stream Logging (Encrypted + Masked) (см. раздел 11).

**Связь с ИКР**: ИКР-7 (данные сами распределяются по подходящим хранилищам) — операционные и форензические логи в разных хранилищах с разным retention.

### 7.2 Противоречие 12: MCP server trust vs extensibility

**Контекст**: § 9.4 Security: «MCP server trust — MVP: explicit config, Production: signed manifests, allow-list». Однако в § 5.2.6 MCPClientManager подключает любой сервер из конфига и автоматически регистрирует его tools. Это означает, что любой, кто может изменить `mcp_servers.json`, может внедрить malicious MCP-сервер, который получит доступ ко всем tools-операциям.

**Улучшаемый параметр** (ТРИЗ #35 «адаптивность» / #15 «динамичность»): динамическое подключение MCP = extensibility.
**Ухудшаемый параметр** (ТРИЗ #31 «надёжность» / #30 «вредные факторы»): arbitrary code execution через MCP = security risk.

**Принципы из матрицы** (35 × 31):
- **Принцип 35 (Изменение параметров)**: изменить «состояние» — каждый MCP-сервер должен иметь подписанный манифест с декларацией разрешённых tools и их side-effects.
- **Принцип 23 (Обратная связь)**: runtime monitoring всех MCP-вызовов — anomaly detection (внезапно `filesystem.delete_file` начал вызываться каждые 5 секунд).
- **Принцип 9 (Предварительное противодействие)**: pre-flight check — при подключении MCP-сервера проверить манифест, подпись, allow-list; отказаться от подключения при несоответствии.
- **Принцип 22 (Превращение вреда в пользу)**: использовать MCP trust requirement как feature — подписанные манифесты становятся «контрактами» для всех tools, не только MCP.

**Архитектурное решение**: комбинированный принцип 35 + 9 + 23. Ввести `MCPManifest` формат:
```yaml
name: filesystem
version: 1.0.0
publisher: modelcontextprotocol
signature: <ed25519 signature>
tools:
  - name: read_file
    side_effects: none
    required_permissions: [filesystem.read]
  - name: write_file
    side_effects: filesystem_mutate
    required_permissions: [filesystem.write]
    requires_user_confirmation: true
  - name: delete_file
    side_effects: destructive
    required_permissions: [filesystem.delete]
    requires_user_confirmation: true
```

`MCPClientManager` при подключении сервера проверяет манифест, сверяет подпись с allow-list (из Vault), и регистрирует только tools из манифеста с указанными правами. Tools с `requires_user_confirmation: true` автоматически попадают в `human_review` node графа. Anomaly detection (принцип 23) — фоновой задачей на основе логов MCP-вызовов.

**Драфт ADR-019**: MCP Server Signed Manifests (см. раздел 11).

**Связь с ИКР**: ИКР-6 (MCP-серверы сами аутентифицируются).

### 7.3 Противоречие 13: RBAC vs usability

**Контекст**: § 9.4 Security: «File access — MVP: по user_id, Production: RBAC + path whitelisting». В MVP у каждого пользователя только свои файлы, что удобно (no friction). В Production — RBAC с ролями (viewer/analyst/admin), что добавляет friction (нужно управлять ролями, запрашивать доступ).

**Улучшаемый параметр** (ТРИЗ #31 «надёжность»): RBAC = granular access control.
**Ухудшаемый параметр** (ТРИЗ #33 «удобство эксплуатации» / #34 «ремонтопригодность»): RBAC = friction, administrative overhead.

**Принципы из матрицы** (31 × 33):
- **Принцип 1 (Дробление)**: разделить ресурсы на «личные» (user-scoped, без RBAC) и «разделяемые» (team/scoped, с RBAC). Личные файлы — без friction, разделяемые — через RBAC.
- **Принцип 13 (Наоборот)**: вместо «запросить доступ» — «предоставить доступ по запросу через auto-approval для типовых случаев» (например, просмотр файла коллеги из той же команды = auto-approve).
- **Принцип 35 (Изменение параметров)**: изменить «состояние» — использовать ABAC (attribute-based) вместо RBAC: доступ определяется атрибутами (команда, проект, метка документа), а не ролью.
- **Принцип 22 (Превращение вреда в пользу)**: использовать запросы доступа как сигнал — частые запросы к одним и тем же ресурсам = кандидат на auto-approval.

**Архитектурное решение**: комбинированный принцип 1 + 35. Ввести гибридную модель:
1. **Personal scope**: файлы, сессии, документы пользователя — без RBAC, только user_id (как в MVP).
2. **Team scope**: документы с меткой `team=...` — доступ по атрибуту team membership (ABAC).
3. **Project scope**: документы с меткой `project=...` — доступ по атрибуту project membership.
4. **Sensitive scope**: документы с меткой `sensitive=true` — явный RBAC с ролями.

Auto-approval (принцип 13): для team/project scope пользователь может запросить временный доступ (1 час / 1 день) с auto-approval, если запрос соответствует политике (например, тот же department, не sensitive).

**Драфт ADR (новый)**: Hybrid ABAC+RBAC Access Control (см. раздел 11).

**Связь с ИКР**: ИКР-0 (функция встроена в инструменты аналитика) — frictionless access в привычном контексте.

### 7.4 Противоречие 14: Тройное векторное хранилище — parity vs feature parity

**Контекст**: ADR-003 фиксирует три адаптера векторных хранилищ. В § Consequences: «Схема коллекций немного отличается (Qdrant использует payload, pgvector — columns)». Это означает, что не все операции (например, hybrid search, filtering by metadata) доступны во всех трёх. Dev на Chroma может работать, а prod на Qdrant — нет (или наоборот).

**Улучшаемый параметр** (ТРИЗ #4 «неоднородность» / #35 «адаптивность»): три адаптера = выбор под окружение.
**Ухудшаемый параметр** (ТРИЗ #14 «стабильность состава» / #36 «сложность устройства»): три разных surface area = разные баги в dev vs prod.

**Принципы из матрицы** (4 × 14):
- **Принцип 3 (Местное качество)**: чётко определить «профиль» каждого адаптера и запретить использование вне профиля.
- **Принцип 5 (Объединение)**: объединить три адаптера в один (pgvector) с двумя режимами (embedded для dev, server для prod). Chroma — только test-double.
- **Принцип 25 (Самообслуживание)**: adapters self-declare capabilities; `RetrieverConfig` выбирает адаптер по capabilities, не по имени.
- **Принцип 1 (Дробление)**: выделить «core VectorStore interface» (только similarity_search) и «extended VectorStore interface» (filtering, hybrid, MMR) — все три поддерживают core, extended — только Qdrant и pgvector.

**Архитектурное решение**: комбинированный принцип 3 + 1. Ввести два уровня интерфейсов:
1. **CoreVectorStore** (similarity_search, add_texts, delete) — поддерживается всеми тремя адаптерами.
2. **ExtendedVectorStore** (hybrid_search, metadata_filtering, MMR, batch operations) — поддерживается Qdrant и pgvector, не Chroma.

Профили адаптеров заданы явно:
- Chroma: dev-only, CoreVectorStore only.
- Qdrant: prod, full ExtendedVectorStore,擅长 high-load.
- pgvector: prod, ExtendedVectorStore, colocated с бизнес-данными.

`RetrieverConfig` выбирает адаптер по требуемому interface: если нужен hybrid_search — Chroma не подходит, автоматически выбирается Qdrant или pgvector. Это делает feature-parity проверяемой на уровне интерфейсов, а не «надеяться, что в dev сработает то же, что в prod».

**Драфт ADR-009 (расширение)**: Layered VectorStore Interfaces (см. раздел 11).

**Связь с ИКР**: ИКР-5 (RAG сам выбирает стратегию) — выбор адаптера по требованиям операции.

### 7.5 Противоречие 15: Локальное файловое хранилище vs multi-instance

**Контекст**: ADR-008 фиксирует `LocalFileStorage` для MVP и `S3FileStorage` для production. В § 8 Trade-offs: «двойная имплементация, нужно тестировать обе». При переходе к multi-instance (3–5 instances за LB) local storage не работает — файл, сохранённый на instance A, не доступен с instance B.

**Улучшаемый параметр** (ТРИЗ #32 «изготовляемость» / #2 «универсальность»): local storage = zero-config для dev.
**Ухудшаемый параметр** (ТРИЗ #14 «стабильность состава» / #35 «адаптивность»): local storage не работает в multi-instance.

**Принципы из матрицы** (32 × 14):
- **Принцип 17 (Переход в другое измерение)**: вынести файловое хранилище в sidecar (MinIO) даже для dev — один docker-compose сервис, не «dual implementation».
- **Принцип 13 (Наоборот)**: вместо абстракции над двумя реализациями — одна реализация (S3-compatible), но с двумя deployment-режимами (embedded MinIO для dev, external MinIO/S3 для prod).
- **Принцип 28 (Замена механики)**: заменить `LocalFileStorage` на `EmbeddedMinIOStorage` — MinIO в in-memory режиме для dev, persistent volume для prod.
- **Принцип 5 (Объединение)**: объединить две реализации в одну с конфигурацией endpoints.

**Архитектурное решение**: принцип 28 + 5. Упразднить `LocalFileStorage` — оставить только `S3CompatibleStorage`. В docker-compose для dev добавляется MinIO как сервис (одна строка в compose), в production — внешний MinIO или AWS S3. Конфигурация: `S3_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_BUCKET` — одинаковая для всех окружений, разница только в значениях. `FileStorage` interface остаётся, но реализация одна.

Дополнительно: для unit-тестов — `InMemoryFileStorage` как test-double (не production-код).

**Драфт ADR (расширение ADR-008)**: Single S3-Compatible File Storage (см. раздел 11).

**Связь с ИКР**: ИКР-7 (данные сами распределяются) + ИКР-0 (функция встраивается в инструменты) — единое хранилище упрощает доступ из IDE/плагинов.

## 8. Su-Field (вепольный) анализ ключевых триад

Su-Field анализ моделирует минимальную техническую систему как триаду из двух веществ (S1, S2) и поля (F), их связывающего. Классификация триады: полная (S1-S2-F присутствуют и полезны), неполная (отсутствует один из элементов), избыточная (лишний элемент), вредная (поле создаёт вредный эффект). Развитие идёт по направлению к полной, эффективной, динамичной веполи.

### 8.1 Триада 1: LLM ↔ Tool Registry ↔ External API

**Текущая модель**:
- S1: LLM (запрос на tool_call)
- S2: External API (Tavily, OpenAI, MCP server)
- F: `tool_registry` + `BaseTool` interface

**Классификация**: полная веполь, но поле `tool_registry` статично — инструменты регистрируются при старте, нет динамического обнаружения.

**Проблема**: при добавлении нового MCP-сервера требуется restart приложения для обновления registry. При удалении tool из API — registry остаётся с «битой» ссылкой.

**Развитие по стандартным решениям**:

**Стандарт 2.2.1 (Переход к динамичной веполи)**: сделать поле `tool_registry` динамичным — tools добавляются/удаляются в runtime через MCP discovery. Реализация — TTL-based cache с periodic refresh.

**Стандарт 1.1.5 (Введение второго поля)**: добавить второе поле — semantic cache tool-вызовов. Теперь триада: LLM → (tool_registry + semantic_cache) → External API. Cache отвечает на повторные запросы без обращения к S2 (External API).

**Идеальная веполь**:
- S1: LLM
- F1: capability-based router (выбирает tool по описанию задачи)
- F2: semantic cache (отвечает на повторные запросы)
- S2: External API

LLM не знает о конкретных tools — она декларирует намерение, router выбирает подходящий tool, cache подменяет вызов при совпадении. ИКР-4 достигается.

### 8.2 Триада 2: User ↔ LangGraph ↔ Checkpoint

**Текущая модель**:
- S1: User message
- S2: Checkpoint storage (PostgreSQL)
- F: LangGraph StateGraph с PostgresSaver

**Классификация**: полная веполь, но поле `PostgresSaver` синхронное и единственное — это «механическое поле» в ТРИЗ-терминологии (низкая эффективность, не поддаётся тонкой настройке).

**Проблема**: каждый node графа блокирует на sync write в PostgreSQL, что суммарно даёт 50–200 мс на типовой агентский цикл. При росте RPS — bottleneck.

**Развитие по стандартным решениям**:

**Стандарт 2.1.1 (Цепная веполь)**: ввести промежуточное вещество — Redis как write-ahead buffer. Триада становится цепной: User → LangGraph → Redis → PostgreSQL. Sync write в Redis (<1 мс), async flush в PostgreSQL (batched).

**Стандарт 3.1.1 (Переход к микроуровню)**: фрагментировать checkpoint — не весь state сохраняется каждый раз, а только delta. Redis хранит delta-ы, PostgreSQL — snapshot + deltas (как в event sourcing).

**Идеальная веполь**:
- S1: User message
- F1: LangGraph с delta-checkpointer (только изменения)
- F2: Redis (hot, sync write)
- S3: PostgreSQL (cold, async snapshot + WAL)
- S2: Checkpoint storage

Checkpointing «сам происходит» — приложение не делает явных save-вызовов, state автоматически персистится через delta. ИКР-2 достигается.

### 8.3 Триада 3: RAG Query ↔ Embeddings ↔ VectorStore

**Текущая модель**:
- S1: Query text
- S2: Vector store (Chroma/Qdrant/pgvector)
- F: Embeddings (OpenAI text-embedding-3-small)

**Классификация**: полная веполь, но поле `Embeddings` единственное (только semantic) — нет второго поля для lexical matching. Это ограничивает recall для запросов с точными термининами (артикулы, имена, коды).

**Проблема**: pure vector retrieval плохо находит точные совпадения (product SKU, error codes). Текущая митигация — «гибридный поиск BM25 + vector» упомянут в § 5.2.5, но не является default.

**Развитие по стандартным решениям**:

**Стандарт 1.1.5 (Введение второго поля)**: добавить второе поле — BM25 lexical index. Триада становится: Query → (Embeddings + BM25) → VectorStore. Hybrid retrieval с fusion (RRF — reciprocal rank fusion).

**Стандарт 2.2.2 (Усиление поля)**: усилить semantic поле — добавить cross-encoder reranker (bge-reranker-base или Cohere Rerank) как post-processing. Получаем три поля: Embeddings (retrieval) + BM25 (retrieval) + Reranker (post-processing).

**Идеальная веполь**:
- S1: Query text
- F1: BM25 (lexical, для точных совпадений)
- F2: Embeddings (semantic, для похожих)
- F3: Cross-encoder reranker (точная переранжировка top-K)
- S2: Document store (векторы + inverted index)

RAG «сам выбирает стратегию» — для запроса с точным кодом BM25 доминирует, для смыслового запроса — Embeddings, reranker уточняет финальный топ. ИКР-5 достигается.

### 8.4 Триада 4: MCP Client ↔ Transport ↔ Server

**Текущая модель**:
- S1: MCPClientManager (запрос call_tool)
- S2: MCP Server (filesystem, github, ...)
- F: Transport (stdio или SSE)

**Классификация**: полная веполь, но поле `Transport` фиксируется в конфиге — нет автоматического выбора. При недоступности stdio (например, в docker) требуется ручное переключение на SSE.

**Проблема**: каждый MCP-сервер в конфиге имеет `transport: "stdio"|"sse"` — это жёсткая связка. В dev удобно stdio, в prod нужен SSE, но переключение требует изменения конфига.

**Развитие по стандартным решениям**:

**Стандарт 2.2.3 (Переход к гибкому полю)**: сделать поле `Transport` гибким — клиент сам определяет оптимальный транспорт. Probe: попробовать SSE (healthcheck endpoint), если недоступен — stdio.

**Стандарт 1.1.1 (Построение полной веполи при неполной)**: добавить третье вещество — `MCPManifest` (подписанный контракт сервера). Триада: Client → (Transport + Manifest) → Server. Manifest декларирует capabilities, transport, подпись.

**Стандарт 3.2.1 (Переход к надсистеме)**: объединить несколько MCP-серверов в один «gateway MCP» — один процесс, который агрегирует несколько MCP-серверов и представляет их как один. Снижает число соединений и упрощает управление.

**Идеальная веполь**:
- S1: MCPClientManager
- F1: Auto-negotiation transport (SSE preferred, stdio fallback)
- F2: Manifest-based trust (signed, allow-listed)
- S3: MCP Gateway (aggregates multiple servers)
- S2: MCP Servers

Transport «сам подбирается», trust «сам проверяется», несколько серверов работают как один. ИКР-6 достигается.

### 8.5 Сводная таблица вепольных триад

| Триада | S1 | S2 | Текущее F | Развитие | Идеальная веполь | ADR |
|---|---|---|---|---|---|---|
| 1 | LLM | External API | tool_registry (статичное) | + semantic cache, + capability router | LLM → (router+cache) → API | ADR-011, ADR-016 |
| 2 | User | Checkpoint | PostgresSaver (sync) | + Redis WAL, + delta checkpointer | User → LangGraph → Redis → PG | ADR-010 |
| 3 | Query | VectorStore | Embeddings (одно поле) | + BM25, + reranker | Query → (BM25+emb+reranker) → Store | ADR-017, ADR-020 |
| 4 | MCP Client | MCP Server | Transport (фиксированный) | + auto-negotiation, + manifest | Client → (transport+manifest+gateway) → Server | ADR-012, ADR-019 |

## 9. Стандартные решения ТРИЗ (5 классов) применённые к архитектуре

Каталог из 76 стандартных решений разбит на 5 классов. Ниже приведены 2–3 применения каждого класса к LLM Client.

### 9.1 Класс 1: Построение и разрушение веполей

**Стандарт 1.1.1 (Построение полной веполи при неполной)**: если есть S1 и S2, но нет F — ввести поле.

Применение: в `Tool Layer` есть LLM (S1) и External API (S2), но связь между ними не имеет явного «поля прав» — любой tool может вызвать любой API. Ввести `ToolPermissions` поле — каждый tool декларирует required permissions, `ToolExecutor` проверяет права перед вызовом. Это делает веполь полной и добавляет audit-trail.

**Стандарт 1.2.1 (Устранение вредного действия поля)**: если поле создаёт вредный эффект — ввести третье вещество, поглощающее вред.

Применение: SSE-стриминг LLM-ответов (поле) создаёт «вредный эффект» — нельзя отменить запрос (one-way). Ввести третье вещество — Redis pub/sub, который передаёт cancel-сигнал из UI в агент, не задействуя SSE-канал. SSE остаётся для данных, Redis — для контроля.

**Стандарт 1.2.2 (Устранение вредного действия вещества)**: если S1 создаёт вред для S2 — ввести третье вещество между ними.

Применение: PII в пользовательских сообщениях (S1) вредит compliance (S2 — логи). Ввести третье вещество — `PIIMasker` (Presidio + custom regex), который стоит между сообщением и логгером. Логи получают маскированный контент, compliance сохранён.

### 9.2 Класс 2: Развитие веполей

**Стандарт 2.1.1 (Цепная веполь)**: если нужно улучшить управление веполью — перейти к цепной веполи, введя промежуточное вещество.

Применение: `LangGraph → PostgreSQL checkpoint` — это «длинная» веполь с большим latency. Ввести промежуточное вещество Redis: `LangGraph → Redis → PostgreSQL`. Redis берёт на себя sync write, PostgreSQL — async persistence. См. ADR-010.

**Стандарт 2.2.1 (Переход к динамичной веполи)**: если веполь фиксированная — сделать её динамичной (параметры поля меняются во времени).

Применение: `tool_registry` фиксирован при старте. Сделать его динамичным — tools добавляются/удаляются в runtime через MCP discovery с TTL. `MCPClientManager` периодически опрашивает серверы, обновляет `tools_cache`. См. противоречие 8.

**Стандарт 2.2.2 (Усиление поля)**: если поле слабое — усилить его (например, магнитное → электромагнитное).

Применение: pure vector retrieval (поле Embeddings) слабое для запросов с точными термининами. Усилить — добавить cross-encoder reranker (более сильное поле для переранжировки top-K). См. ADR-017.

**Стандарт 2.2.4 (Переход к измерительной веполи)**: если поле только передаёт действие — добавить измерительную функцию.

Применение: `LLM Provider` поле (`BaseChatModel` interface) только передаёт запрос-ответ. Добавить измерительную функцию — `LLMCallMetrics` (latency, tokens, cost, success rate). Метрики используются `LLMRouter` для adaptive routing. См. ADR-015.

### 9.3 Класс 3: Переход к надсистеме и микроуровню

**Стандарт 3.1.1 (Переход к микроуровню)**: если веполь исчерпала развитие — перейти на микроуровень (дробление веществ).

Применение: `file_export` tool — монолитная функция, обрабатывающая все 8 форматов. Перейти на микроуровень — разделить на `Renderer` для каждого формата (md, txt, pdf, docx, xlsx, odt), каждый со своим интерфейсом. `file_export` становится dispatcher, не монолитом. Это уже частично сделано в § 10 структуры репозитория (`renderers/`), но интерфейс рендереров не формализован.

**Стандарт 3.1.4 (Дробление поля)**: если поле неделимо — разделить его на несколько полей с разными свойствами.

Применение: `tool_calling` поле (одно для всех моделей). Разделить на `NativeToolCalling` (для моделей с function calling) и `ReActToolCalling` (для моделей без). Adapter выбирает поле по capability matrix. См. ADR-016.

**Стандарт 3.2.1 (Переход в надсистему)**: если система исчерпала развитие — объединить с другой системой в надсистему.

Применение: LLM Client как standalone приложение исчерпал развитие в направлении «chat UI» (много конкурентов). Перейти в надсистему — стать MCP-сервером для других агентов/IDE. Это ADR-004 (MCP Server mode), который ТРИЗ-анализ рекомендует ускорить до Phase 3 вместо Phase 6.

### 9.4 Класс 4: Детектирование и измерение

**Стандарт 4.1.1 (Измерение без изменения системы)**: если нужно измерить параметр — сделать это «пассивно», без вмешательства.

Применение: измерение «достаточности ответа» (для замены `max_iterations`). Не вводить дополнительный LLM-вызов-судью (дорого), а использовать пассивные метрики: cosine similarity между последними двумя сообщениями state, длина ответа в токенах, presence of citations. Если все метрики стабильны — ответ «достаточен».

**Стандарт 4.2.2 (Измерение через разрушение)**: если прямое измерение невозможно — разрушить часть системы и измерить эффект.

Применение: измерение «качества RAG» — невозможно напрямую. Разрушить — отключить reranker на 10% запросов, измерить изменение recall@10 через user feedback (thumbs up/down). A/B test как ТРИЗ-измерение.

**Стандарт 4.3.1 (Измерение через копирование)**: если прямое измерение нарушает систему — измерить копию.

Применение: измерение производительности графа агента под нагрузкой. Не нагружать production, а создать synthetic load test (replay логов с маскированными данными) в staging. Это уже частично делается (`scripts/load_test.py`), но не регулярно.

### 9.5 Класс 5: Введение веществ и полей

**Стандарт 5.1.1 (Введение вещества извне)**: если не хватает вещества для построения веполи — ввести его извне.

Применение: для circuit breaker (LLM router) нужно «вещество» — метрика «текущая нагрузка на провайдера». Этого нет в LLM Client. Ввести извне — external observability (Prometheus + Grafana) уже собирает latency/error rate провайдеров; router читает эти метрики как external substance.

**Стандарт 5.2.1 (Введение поля извне)**: если не хватает поля — ввести его извне.

Применение: для anomaly detection MCP-вызовов нужно «поле» — модель аномалий. Нет смысла строить свою — ввести внешнее поле (Datadog Anomaly Detection или simple Z-score на метриках в Prometheus).

**Стандарт 5.3.1 (Введение производного вещества)**: если введение вещества создаёт вред — ввести производное (модифицированное) вещество.

Применение: для semantic cache LLM-ответов нужно «вещество» — кэш. Но прямой кэш (exact match) бесполезен (редко повторяются точные запросы). Ввести производное вещество — semantic cache с embedding similarity threshold. Кэш «модифицирован» для работы с семантикой, не с точным совпадением. См. ADR-011.

## 11. Драфты новых ADR (ADR-009 — ADR-020)

Каждый ADR оформлен по шаблону `ARCHITECT.md` § 7: Status / Context / Decision / Consequences. Все драфты имеют Status `Proposed` и подлежат ревью на архитектурном комитете.

### ADR-009: Plugin-based VectorStore Registry

**Status**: Proposed (2026-09-20)
**Context**: ADR-003 вводит три адаптера векторных хранилищ через `VectorStoreFactory` с `match kind:`. Это создаёт три проблемы: (1) добавление нового адаптера требует изменения factory; (2) выбор адаптера по имени, а не по capabilities; (3) три разных surface area для тестирования. ТРИЗ-противоречие C-3 и C-14 указывают на необходимость развязки «способ выбора» и «имплементация».
**Decision**: Заменить `VectorStoreFactory` на `VectorStoreRegistry`, наполняемый через entrypoints (`pyproject.toml` `[project.entry-points."llm_client.vector_stores"]`). Каждый адаптер декларирует: имя, профиль (`embedded`/`distributed`/`colocated_with_pg`), поддерживаемые интерфейсы (`CoreVectorStore`, `ExtendedVectorStore`). `RetrieverConfig` выбирает адаптер по профилю и требуемому интерфейсу, не по имени. Ввести два уровня интерфейсов:
- `CoreVectorStore`: `similarity_search`, `add_texts`, `delete` — поддерживается всеми.
- `ExtendedVectorStore`: `hybrid_search`, `metadata_filtering`, `mmr_search`, `batch_upsert` — поддерживается Qdrant и pgvector, не Chroma.
**Consequences**:
- (+) Новые адаптеры добавляются без изменения core-кода.
- (+) Feature-parity проверяема на уровне интерфейсов.
- (+) Chroma явно позиционируется как dev-only, не вводит в заблуждение.
- (-) Дополнительная абстракция (два интерфейса вместо одного).
- (-) Требуется рефакторинг существующего `VectorStoreFactory`.

### ADR-010: Async Checkpoint Write-Behind Log

**Status**: Proposed
**Context**: ADR-001 использует `PostgresSaver` для LangGraph checkpointer с синхронной записью в `agent_checkpoints` на каждом node transition. Это добавляет 10–50 мс на каждый переход, суммарно 50–200 мс на типовой агентский цикл, что становится bottleneck при росте RPS. ТРИЗ-противоречие C-2 требует развязки latency и durability.
**Decision**: Ввести composite checkpointer `RedisPostgresCheckpointer`:
1. `RedisCheckpointer` — synchronous write в Redis (latency <1 мс, TTL=24h).
2. `PostgresCheckpointer` — asynchronous batched write (background task каждые 5 сек или N checkpoints).
3. Восстановление при restart: сначала из PostgreSQL (snapshot), затем replay из Redis (delta).
4. `BaseCheckpointSaver` interface остаётся совместимым с LangGraph.
**Consequences**:
- (+) Latency checkpointing снижается с 10–50 мс до <1 мс.
- (+) PostgreSQL не нагружается на каждом node transition.
- (+) Resume-after-restart сохраняется (Redis + PostgreSQL).
- (-) Добавляется Redis как mandatory dependency для checkpointing (раньше опциональный).
- (-) Возможна потеря последних 5 сек checkpoint-ов при одновременном отказе Redis и PostgreSQL.
- (-) Сложнее тестировать (два хранилища вместо одного).

### ADR-011: Hybrid Semantic Cache for LLM

**Status**: Proposed
**Context**: § 12 Q-5 фиксирует риск стоимости LLM при >50k токенов контекста. Текущая митигация (context compression, map-reduce) снижает, но не устраняет проблему. ТРИЗ-противоречие C-6 указывает на необходимость кэширования на уровне LLM-ответов, не только embeddings.
**Decision**: Ввести three-tier cache:
1. **Tier 3 — Semantic answer cache**: cache полных LLM-ответов по embedding similarity запроса. Threshold: cosine similarity > 0.92. Storage: Redis с TTL=24h. Invalidation: при изменении любого документа в RAG, на который ссылался ответ.
2. **Tier 1 — Facts cache**: при индексации документа извлекаются факты (LLM-call), хранятся в `documents_facts` таблице, индексируются в векторном хранилище как metadata.
3. **Tier 2 — Vector retrieval** остаётся как есть, но с reranker (см. ADR-017).
**Consequences**:
- (+) Среднее число токенов в контексте LLM снижается на 60–80%.
- (+) Повторные запросы возвращают ответ из cache (latency <100 мс вместо 5–30 сек).
- (-) Risk stale answers — требуется аккуратная инвалидация.
- (-) Дополнительный LLM-call при индексации (но одноразовый, не per-request).
- (-) Хранение embeddings ответов в Redis увеличивает memory footprint.

### ADR-012: MCP Transport Auto-Negotiation

**Status**: Proposed
**Context**: § 12 Q-3 фиксирует сложность MCP-серверов с stdio в docker-compose. Текущая конфигурация `mcp_servers.json` жёстко задаёт `transport: "stdio"|"sse"` для каждого сервера. ТРИЗ-противоречие C-8 требует развязки выбора транспорта от конфигурации.
**Decision**: Ввести `MCPTransport` абстракцию:
1. `MCPTransport` interface с методами `probe()`, `connect()`, `call_tool()`, `list_tools()`.
2. `StdioTransport` — для dev, subprocess.
3. `SSETransport` — для docker/prod, HTTP+SSE.
4. При подключении сервера `MCPClientManager` probe-ит оба транспорта (SSE healthcheck, stdio spawn) и выбирает живой.
5. Конфигурация `mcp_servers.json` опционально содержит `transport`, но если не указан — auto-negotiation.
6. В docker-compose каждый MCP-сервер — отдельный сервис с healthcheck.
**Consequences**:
- (+) Dev/prod parity: один конфиг работает везде.
- (+) Изоляция MCP-серверов в docker (sidecar, не subprocess).
- (+) Cold start MCP-серверов устраняется (долгоживущие сервисы).
- (-) Дополнительная сложность в `MCPClientManager`.
- (-) Для stdio-серверов без SSE-режима требуется обёртка (mcp-proxy).

### ADR-013: SSE + HTTP Cancel Endpoint

**Status**: Proposed
**Context**: ADR-007 зафиксировал SSE для streaming LLM-ответов, но отметил: «One-way only: для интерактивных прерываний нужен доп. HTTP endpoint». ТРИЗ-противоречие C-4 указывает на необходимость явной control-plane.
**Decision**: Ввести dual-channel архитектуру:
1. **Data-plane**: SSE для streaming tokens от агента к UI (без изменений).
2. **Control-plane**: HTTP POST `/sessions/{id}/cancel` + Redis pub/sub `session:{id}:cancel` для уведомления агента.
3. На стороне агента — `CancellationToken`, проверяемый между node-ами графа. При получении cancel-сигнала граф прерывает upstream LLM-вызов и возвращает partial answer.
4. UI-клиент детектирует обрыв SSE-соединения (visibility change / beforeunload) и автоматически шлёт cancel.
**Consequences**:
- (+) Cancel работает мгновенно (Redis pub/sub latency <5 мс).
- (+) Авто-cancel при закрытии вкладки — UX improvement.
- (+) Не нарушает ADR-007 (SSE остаётся для данных).
- (-) Добавляется Redis pub/sub как dependency для control-plane.
- (-) Граф должен явно проверять `CancellationToken` — дополнительный код в каждом node.

### ADR-014: Dual-Stream Logging (Encrypted + Masked)

**Status**: Proposed
**Context**: § 9.4 Security требует PII masking, § 9.6 Observability требует full trace retention 90 дней. Противоречие: маскирование ломает воспроизводимость, отсутствие маскирования ломает compliance. ТРИЗ-противоречие C-11 указывает на разделение потоков.
**Decision**: Ввести `DualStreamLogger`:
1. **Operational stream**: маскированный (Presidio + custom regex), отправляется в stdout/Loki/ELK, retention 30 дней. Используется командой для debugging.
2. **Forensic stream**: зашифрованный (AES-256-GCM с ключом из Vault/KMS), отправляется в отдельное S3 bucket с server-side encryption, retention 90+ дней. Доступ через отдельный RBAC (security officer + аудит-комитет).
3. PII detection score сохраняется в `messages` таблице как metadata для аналитики.
4. В dev-окружении forensic stream отключён, только operational.
**Consequences**:
- (+) Compliance удовлетворён (PII не в operational логах).
- (+) Воспроизводимость сохранена (forensic логи).
- (+) Аналитика по sensitive data (через PII score).
- (-) Двойная стоимость хранения логов.
- (-) Сложность доступа к forensic (отдельный RBAC, аудит).
- (-) Ключи шифрования в KMS — ещё одна зависимость.

### ADR-015: Cost-Aware Routing

**Status**: Proposed
**Context**: § 5.2.3 описывает `fallback_chain` — автоматический fallback при 5 ошибках подряд. Это не учитывает стоимость (GPT-4o vs Claude 3.5 Sonnet различаются в 1.7×) и не предотвращает превышение бюджета. ТРИЗ-противоречие C-7 указывает на необходимость routing вместо fallback.
**Decision**: Заменить `fallback_chain` на `LLMRouter`:
1. `LLMRouter` хранит политики выбора (`cost_priority`, `latency_priority`, `quality_priority`, `privacy_priority`).
2. На каждый запрос router учитывает: текущую нагрузку на провайдера (circuit breaker), текущий расход бюджета (cost guard), требования к приватности (zero-retention policy), capability matrix модели (см. ADR-016).
3. При достижении 80% месячного бюджета автоматически переключается на cheapest available (GPT-4o-mini / Claude Haiku / Ollama).
4. Fallback — крайний случай; обычно routing распределяет трафик 70/30 между провайдерами.
5. Метрики от `token_usage_tracker` и `cost_tracker` идут в router в real-time.
**Consequences**:
- (+) Предсказуемость стоимости (cost guard).
- (+) Availability выше (load balancing вместо fallback).
- (+) Поддержка Ollama как cheap-tier.
- (-) Усложнение LLM Provider Layer.
- (-) Возможны surprises: router выбрал GPT-4o-mini вместо GPT-4o — нужно явное логирование.

### ADR-016: Tool Capability Adapter

**Status**: Proposed
**Context**: ADR-006 зафиксировал нативный tool calling через `bind_tools()`, что блокирует модели без function calling (Llama 3.1 base). Это противоречит плану Phase 4 (Ollama). ТРИЗ-противоречие C-9 требует развязки «описание tool» и «способ вызова».
**Decision**: Ввести `ModelCapabilityMatrix` и `ToolCallingAdapter`:
1. `ModelCapabilityMatrix` — для каждой модели декларируются: `supports_native_tools`, `supports_streaming`, `supports_vision`, `context_window`, `cost_per_1m_tokens`, `latency_p50`, `latency_p99`.
2. `ToolCallingMode` enum: `native` (function calling API), `react` (system prompt emulation), `hybrid` (native с fallback на ReAct при ошибке парсинга).
3. `ToolCallingAdapter` выбирает режим по capability matrix.
4. Для моделей без native function calling автоматически включается ReAct-эмуляция.
5. `LLMRouter` (ADR-015) использует capability matrix для маршрутизации.
**Consequences**:
- (+) Поддержка локальных моделей (Ollama, Llama, Mistral) без function calling.
- (+) Явные capabilities вместо неявных предположений.
- (+) ReAct как fallback для любой модели.
- (-) ReAct-эмуляция менее надёжна, чем native tool calling.
- (-) Поддержка двух режимов = больше кода в adapter.

### ADR-017: Reranker Model in RAG

**Status**: Proposed
**Context**: § 5.2.5 упоминает MMR reranking, но без ML-reranker. ТРИЗ-противоречие C-6 требует усиления поля retrieval (стандарт 2.2.2). Cross-encoder reranker даёт значительное улучшение precision (типично +20–30% recall@5).
**Decision**: Ввести cross-encoder reranker в RAG pipeline:
1. Default reranker: `bge-reranker-base` (локальная модель, нет external API).
2. Опционально: Cohere Rerank API (если доступен и budget позволяет).
3. Pipeline: vector retrieval (top-20) → BM25 retrieval (top-20) → fusion (RRF, top-50) → reranker (top-5).
4. Reranker — pluggable через `RerankerRegistry` (как VectorStore в ADR-009).
**Consequences**:
- (+) Значительное улучшение precision и recall.
- (+) Снижение контекста LLM (5 качественных чанков вместо 20 шумных).
- (-) Дополнительная latency (50–200 мс на reranking).
- (-) bge-reranker-base требует ~600MB RAM для in-process.
- (-) Cohere Rerank — внешняя зависимость с отдельной стоимостью.

### ADR-018: External Session Store for Streamlit

**Status**: Proposed
**Context**: ADR-002 фиксирует Streamlit для MVP, признаёт проблему multi-instance (sticky session). ТРИЗ-противоречие C-1 требует развязки session state от конкретного инстанса.
**Decision**: Ввести `SessionStore` abstraction с реализацией `RedisSessionStore`:
1. `SessionStore` interface: `get_session(id)`, `save_session(id, state)`, `list_sessions(user_id)`.
2. `RedisSessionStore` — primary, TTL=24h, JSON serialization.
3. `LocalSessionStore` — для unit-тестов.
4. Streamlit `session_state` синхронизируется с `SessionStore` через callback.
5. `UIClient` abstraction (см. противоречие C-1) позволяет переключать UI backend без потери session state.
**Consequences**:
- (+) Multi-instance без sticky session.
- (+) Session survives Streamlit restart.
- (+) Путь к Chainlit/FastAPI без переписывания session logic.
- (-) Redis становится mandatory dependency.
- (-) Сериализация session_state в JSON — потенциальные проблемы с custom types.

### ADR-019: MCP Server Signed Manifests

**Status**: Proposed
**Context**: § 9.4 Security фиксирует «MCP server trust — Production: signed manifests, allow-list», но формат манифеста и механизм проверки не определены. ТРИЗ-противоречие C-12 требует развязки extensibility и security.
**Decision**: Ввести `MCPManifest` формат (YAML, ed25519 signed):
1. Manifest содержит: `name`, `version`, `publisher`, `signature`, `tools[]` с `name`, `side_effects`, `required_permissions`, `requires_user_confirmation`.
2. `MCPClientManager` при подключении сервера: проверяет подпись по allow-list (из Vault), регистрирует только tools из манифеста.
3. Tools с `requires_user_confirmation: true` автоматически попадают в `human_review` node графа.
4. Manifest хранится в `mcp_servers/{name}/manifest.yaml` в репозитории MCP-сервера.
5. Anomaly detection (фоновая задача) — Z-score на частоте вызовов каждого tool.
**Consequences**:
- (+) Явный контракт для MCP-серверов.
- (+) Destructive операции требуют подтверждения пользователя.
- (+) Anomaly detection как defence-in-depth.
- (-) Разработчикам MCP-серверов нужно генерировать подписи.
- (-) Allow-list в Vault — дополнительная операционная нагрузка.

### ADR-020: Hybrid (BM25 + Vector) RAG по умолчанию

**Status**: Proposed
**Context**: § 5.2.5 упоминает hybrid search (BM25 + vector), но как опция. Pure vector retrieval плохо находит точные совпадения (product SKU, error codes). ТРИЗ-стандарт 1.1.5 требует второго поля в triаде Query↔Embeddings↔VectorStore.
**Decision**: Сделать hybrid retrieval (BM25 + vector) default:
1. В `RetrieverConfig` добавить `retrieval_strategy: "vector"|"bm25"|"hybrid"` (default: `hybrid`).
2. BM25 index строится параллельно с vector index при индексации документа.
3. Hybrid retrieval: vector top-20 + BM25 top-20 → RRF fusion → top-K.
4. Reranker (см. ADR-017) применяется после fusion.
5. Хранение: `documents` таблица получает полнотекстовый индекс (PostgreSQL `tsvector` или OpenSearch).
**Consequences**:
- (+) Значительное улучшение recall для запросов с точными терминами.
- (+) Best of both worlds: semantic + lexical.
- (-) Дополнительное хранилище для BM25 index.
- (-) Latency retrieval возрастает на 30–50% (двойной запрос).
- (-) Reranker обязателен (без него noise от fusion).

## 13. Риски и встречные противоречия при внедрении

### 13.1 Риск over-engineering

ТРИЗ-анализ предлагает 12 новых ADR. Внедрение всех разом превратит архитектуру в «франкенштейна» с избыточной абстракцией. Контр-мера: внедрять только те ADR, которые явно соответствуют текущей фазе roadmap. ADR-019 (signed manifests) не нужен в Phase 1, его внедрение в MVP — over-engineering.

**Встречное противоречие**: ТРИЗ-анализ рекомендует много абстракций (UIClient, MCPTransport, VectorStoreRegistry, ToolCallingAdapter), но каждая абстракция — это кривая обучения и потенциальная точка отказа. Применить принцип ТРИЗ #16 (частичное/избыточное действие): внедрять абстракцию «избыточно» (полный interface), но имплементировать «частично» (одна реализация). Когда появится вторая реализация — interface уже готов.

### 13.2 Риск конфликта с существующими ADR

Некоторые новые ADR явно противоречат существующим:
- ADR-015 (Cost-aware router) противоречит ADR-002 (плану fallback chain) — fallback удаляется.
- ADR-018 (External session) противоречит ADR-002 (Streamlit native session_state) — требуется sync layer.
- (расш. ADR-008) Single S3 storage противоречит ADR-008 (LocalFileStorage для MVP) — local упраздняется.

Контр-мера: каждый новый ADR должен содержать явный раздел `Supersedes:` с указанием заменяемых ADR и `Migration plan:`. Архитектурный комитет ревьюит conflicts перед approval.

### 13.3 Риск кривой обучения

`UIClient`, `MCPTransport`, `VectorStoreRegistry`, `ToolCallingAdapter`, `LLMRouter`, `ModelCapabilityMatrix`, `DualStreamLogger` — 7 новых абстракций. Команда из 2 разработчиков может потратить больше времени на освоение, чем на имплементацию.

Контр-мера: каждая абстракция должна сопровождаться ADR-документом, код-примером и unit-test-паттерном. Onboarding-session для каждой новой абстракции. Метрика: «время от onboarding до первого PR» ≤ 2 дня.

### 13.4 Риск «ложной зрелости»

После внедрения 12 ADR система может казаться «зрелой», но фактически быть перегруженной. Метрики идеальности (из закона 4.4) должны отслеживаться: `delta функциональности / delta сложности ≥ 1`. Если после внедрения ADR метрика падает — ADR нужно откатить.

### 13.5 Риск зависимости от внешних сервисов

Новые ADR добавляют зависимости: KMS/Vault (ADR-014), Cohere Rerank (опционально в ADR-017), Prometheus metrics (ADR-015). Каждая зависимость — потенциальный single point of failure.

Контр-мера: каждая новая зависимость должна иметь in-process fallback или degrade-gracefully поведение. Например, KMS недоступен → forensic stream переключается на local encrypted file; Cohere Rerank недоступен → fallback на bge-reranker-base.

### 13.6 Тест-кейсы для проверки гипотез

Перед полным внедрением каждого ADR — пилотный тест:

| ADR | Пилот | Метрика успеха | Критерий отката |
|---|---|---|---|
| ADR-010 | 1 неделя на staging | Latency checkpoint <2 мс | Потеря состояния при restart |
| ADR-011 | 100 запросов на staging | Hit rate cache >15% | Stale answers >1% |
| ADR-013 | 1 sprint на dev | Cancel latency <100 мс | Cancel не доходит до LLM |
| ADR-014 | Audit на staging | PII leaks = 0 | Forensic stream недоступен >1 час |
| ADR-015 | 1 месяц shadow mode | Cost predictability ±10% | Cost overrun >20% |
| ADR-017 | A/B test 2 недели | Recall@5 ↑ 15% | Latency retrieval ↑ >100 мс |
| ADR-020 | A/B test 1 неделя | Recall ↑ для точных терминов | Latency retrieval ↑ >50% |

Пилот провалился → ADR пересматривается, не внедряется. Пилот успешен → full rollout.

## 14. Заключение и следующие шаги

### 14.1 Сводка результатов

ТРИЗ-анализ архитектуры LLM Client (v1.0.0) выявил 15 технических противоречий, 4 ключевые вепольные триады и 16 применений стандартных решений. Из 15 противоречий:
- 8 имеют приоритет High (блокируют Production).
- 7 имеют приоритет Medium (ухудшают качество).

Для разрешения сформулированы 12 новых ADR (ADR-009 — ADR-020) и 3 расширения существующих ADR. Все ADR привязаны к фазам ROADMAP; суммарная оценка внедрения ~110 чел-дн.

**Ожидаемый рост идеальности системы** (по закону 4.4):
- Функциональность: +4 новые capability (semantic cache, cost-aware routing, MCP server mode, hybrid RAG).
- Сложность: +7 абстракций, но −2 упразднённых (LocalFileStorage, fallback_chain).
- Чистая дельта идеальности: положительная при условии соблюдения метрики «delta f / delta complexity ≥ 1».

### 14.2 Главные ТРИЗ-инсайты

1. **ИКР-0 направляет к надсистеме**: LLM Client не должен быть standalone-продуктом — функция должна встроиться в инструменты аналитика. Это ускоряет ADR-004 (MCP Server mode) до Phase 3.

2. **Законы развития вскрывают дисбаланс**: RAG Layer переразвит (три хранилища), Presentation Layer отстаёт (Streamlit single-instance). Заморозить RAG, направить ресурсы на UI и Security.

3. **Вепольный анализ показывает «слабые поля»**: sync PostgreSQL checkpoint, single Embeddings field в RAG, фиксированный MCP transport — все «механические поля», требующие перехода в «электромагнитные» (динамичные, множественные).

4. **Стандартные решения дают готовые паттерны**: цепная веполь (Redis WAL), усиление поля (reranker), переход к гибкому полю (auto-negotiation transport), производное вещество (semantic cache) — все применимы напрямую.

### 14.3 Следующие шаги

1. **Архитектурный комитет**: ревью всех 12 драфтов ADR на ближайшем заседании. Решение по каждому: Approved / Rejected / Needs revision. Срок: 2 недели.

2. **Пилотное внедрение 2 ADR**: выбрать ADR-013 (SSE+cancel) и (расш. ADR-008) Single S3 storage как quick wins. Срок: 1 sprint.

3. **Метрики идеальности**: добавить в observability dashboard метрику «delta функциональности / delta сложности» (через LOC + ADR count + capability count). Срок: до конца Phase 1.

4. **Triage оставшихся рисков**: Q-1 (Ollama), Q-2 (LangSmith pricing), Q-4 (Streamlit+async) из § 12 ARCHITECT.md требуют отдельных ТРИЗ-разборов. Срок: Phase 2.
